================================================================================
  TOPSHELF INVENTORY — MOBILE API REFERENCE
  Base URL: https://www.topshelfInventory.com
  All data is scoped to the authenticated user's organization.
================================================================================


────────────────────────────────────────────────────────────────────────────────
OVERVIEW
────────────────────────────────────────────────────────────────────────────────

All mobile API endpoints live under /api/mobile/.

Authentication uses JWT Bearer tokens — not cookies.
  1. Call POST /api/mobile/auth to get a token.
  2. Include the token in every subsequent request:
       Authorization: Bearer <your-token>

Tokens expire after 7 days. Store them securely:
  iOS    → Keychain (via react-native-keychain or expo-secure-store)
  Android → EncryptedSharedPreferences or Keystore

Every response is JSON. Every request body must be JSON with the header:
  Content-Type: application/json

All data returned is filtered to the authenticated user's organization —
no cross-organization data leakage is possible.


────────────────────────────────────────────────────────────────────────────────
1. AUTHENTICATION — Login and get a token
────────────────────────────────────────────────────────────────────────────────

POST /api/mobile/auth

No Authorization header needed for this request.

REQUEST BODY:
{
  "organization_subdomain": "your-bar",     ← required (your org's subdomain)
  "email": "admin@yourbar.com",             ← use EITHER email+password
  "password": "yourpassword"
}

OR:
{
  "organization_subdomain": "your-bar",
  "pin": "1234"                             ← OR a 4-digit PIN
}

RESPONSE (200 OK):
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expires_in": 604800,
  "user": {
    "id": 42,
    "first_name": "Alex",
    "last_name": "Smith",
    "email": "admin@yourbar.com",
    "role": "admin",
    "permissions": ["all"]
  },
  "organization": {
    "id": 7,
    "name": "The Rusty Nail",
    "subdomain": "your-bar",
    "subscription_plan": "pro"
  }
}

ERROR RESPONSES:
  401 { "error": "Invalid credentials" }
  401 { "error": "Invalid PIN" }
  404 { "error": "Organization not found" }
  400 { "error": "Provide email+password or pin" }

USAGE AFTER LOGIN:
  Save the "token" value and send it on every future request:
    Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...


────────────────────────────────────────────────────────────────────────────────
2. REGISTRATION — Join via admin invite link
────────────────────────────────────────────────────────────────────────────────

Admins generate invite links from Settings → Users → "Invite New User by Email."
The link looks like:
  https://www.topshelfInventory.com/register/invite?token=abc123...

The token in that URL is what the mobile app uses. No Authorization header
is needed for either registration endpoint.

── Step 1: Validate the token ──────────────────────────────────────────────────

GET /api/mobile/register?token=<invite-token>

RESPONSE (200 OK):
{
  "valid": true,
  "org_name": "The Rusty Nail",
  "email": "newstaff@yourbar.com",   ← pre-filled email (may be null)
  "role": "user"
}

ERROR RESPONSES:
  404 { "error": "Invalid token" }
  410 { "error": "Invitation already used" }
  410 { "error": "Invitation expired" }

── Step 2: Complete registration ────────────────────────────────────────────────

POST /api/mobile/register

REQUEST BODY:
{
  "token": "abc123...",              ← required — from the invite link
  "firstName": "Alex",              ← required
  "lastName": "Smith",              ← required
  "displayName": "Alex S.",         ← optional (shown in feed & messages)
  "email": "alex@yourbar.com",      ← required if not pre-filled by admin
  "phone": "5550001234",            ← optional
  "password": "mysecurepassword",   ← required, min 6 characters
  "pin": "1234"                     ← required, exactly 4 digits
}

RESPONSE (200 OK):
{
  "token": "eyJhbGciOiJIUzI1NiIs...",   ← save this, use as Bearer token
  "expires_in": 604800,
  "user": {
    "id": 55,
    "first_name": "Alex",
    "last_name": "Smith",
    "role": "user",
    "email": "alex@yourbar.com"
  },
  "organization": {
    "id": 7,
    "name": "The Rusty Nail"
  }
}

ERROR RESPONSES:
  400 { "error": "First and last name are required" }
  400 { "error": "Password must be at least 6 characters" }
  400 { "error": "PIN must be exactly 4 digits" }
  409 { "error": "Email already in use" }
  410 { "error": "Invitation already used" }
  410 { "error": "Invitation expired" }

NOTE: Each invite token can only be used once. After successful registration,
use the returned "token" exactly like any other Bearer token for all subsequent
API calls. The user is automatically assigned to all locations in the org.


────────────────────────────────────────────────────────────────────────────────
3. DEVICE TOKENS — Push notification registration
────────────────────────────────────────────────────────────────────────────────

Call these after login and whenever the FCM/APNs token refreshes.
Push notifications require Firebase FCM to be configured on the server.
If not configured, push is silently disabled but all other API calls work normally.

POST /api/mobile/device-token

REQUEST BODY:
{
  "token": "fcm-or-apns-token-string",
  "platform": "ios"    ← or "android"
}

RESPONSE (200 OK):
  { "ok": true }

── Unregister on logout ─────────────────────────────────────────────────────────

DELETE /api/mobile/device-token

REQUEST BODY:
  { "token": "specific-token" }    ← omit to remove ALL tokens for this user

RESPONSE (200 OK):
  { "ok": true }

4. NOTIFICATIONS — In-app notification inbox
────────────────────────────────────────────────────────────────────────────────

GET /api/mobile/notifications

QUERY PARAMETERS (all optional):
  ?unread_only=true    Only return unread notifications
  ?limit=30            Max to return (default: 30, max: 100)

RESPONSE (200 OK):
{
  "notifications": [
    {
      "id": 10,
      "type": "swap_request",
      "title": "🔄 Shift Swap Request",
      "message": "Alex Smith wants to swap shifts with you on 2026-05-10",
      "data": { "swap_id": "42", "type": "swap_request" },
      "is_read": false,
      "created_at": "2026-05-04T18:00:00Z"
    }
  ],
  "unread_count": 3
}

── Mark as read ─────────────────────────────────────────────────────────────────

PATCH /api/mobile/notifications

REQUEST BODY:
  { "id": 10 }    ← omit id to mark ALL notifications as read

RESPONSE (200 OK):
  { "ok": true }


────────────────────────────────────────────────────────────────────────────────
5. DASHBOARD FEED — Organization activity posts
────────────────────────────────────────────────────────────────────────────────

GET /api/mobile/feed

QUERY PARAMETERS (all optional):
  ?page=1        Page number (default: 1)
  ?limit=20      Results per page (max: 50, default: 20)

RESPONSE (200 OK):
{
  "posts": [
    {
      "id": 101,
      "content": "Counted the liquor shelf — all good!",
      "images": ["data:image/jpeg;base64,/9j/4AAQ..."],
      "tagged_user_ids": [3, 8],
      "created_at": "2026-04-30T14:22:00Z",
      "user_id": 5,
      "author_name": "Alex Smith",
      "author_avatar": "data:image/jpeg;base64,...",
      "like_count": 4,
      "comment_count": 2,
      "liked_by_me": false
    }
  ],
  "total": 84,
  "page": 1,
  "users": [
    { "id": 3, "display_name": "Jamie Lee", "profile_picture": null },
    { "id": 8, "display_name": "Morgan D.", "profile_picture": "data:image/jpeg;base64,..." }
  ]
}

NOTES:
- "images" is an array of base64 data-URL strings. Decode and display directly.
- "tagged_user_ids" references IDs in the "users" array returned alongside posts.
- "like_count" / "comment_count" / "liked_by_me" are pre-computed for the feed.
- Posts are returned newest-first. Paginate with ?page=2, ?page=3, etc.

── Create a post ────────────────────────────────────────────────────────────────

POST /api/mobile/feed

REQUEST BODY:
{
  "content": "Just finished the audit!",   ← at least one of content or images required
  "images": ["data:image/jpeg;base64,..."],
  "tagged_user_ids": [3, 8]
}

RESPONSE (200 OK):
  { "ok": true, "id": 102, "created_at": "2026-05-04T19:00:00Z" }

── Like / Unlike a post ─────────────────────────────────────────────────────────

POST /api/mobile/feed/like?id=<postId>

No request body needed.

RESPONSE (200 OK):
  { "liked": true, "count": 5 }   ← "liked" is the new state after toggle

── Comments ─────────────────────────────────────────────────────────────────────

GET /api/mobile/feed/comments?postId=<id>

RESPONSE (200 OK):
{
  "comments": [
    {
      "id": 7,
      "content": "Great work!",
      "created_at": "2026-05-04T19:10:00Z",
      "user_id": 3,
      "author_name": "Jamie Lee",
      "author_avatar": null
    }
  ]
}

POST /api/mobile/feed/comments?postId=<id>

REQUEST BODY:
  { "content": "Looks good!" }

RESPONSE (200 OK):
{
  "ok": true,
  "comment": {
    "id": 8,
    "content": "Looks good!",
    "created_at": "2026-05-04T19:15:00Z",
    "user_id": 42,
    "author_name": "Alex Smith",
    "author_avatar": null
  }
}

DELETE /api/mobile/feed/comments?id=<commentId>

Can only delete your own comments. Admins can delete any comment.

RESPONSE (200 OK):
  { "ok": true }

6. BARRED LIST — Persons barred from the venue
────────────────────────────────────────────────────────────────────────────────

GET /api/mobile/barred

QUERY PARAMETERS (all optional):
  ?trespassed_only=true    Only return persons with a formal trespass order

RESPONSE (200 OK):
{
  "barred": [
    {
      "id": 1,
      "name": "John Doe",
      "aliases": ["Johnny D", "JD"],
      "photo": "data:image/jpeg;base64,...",
      "description": "Involved in assault incident on 2026-03-12.",
      "barred_by_name": "Alex Smith",
      "trespassed": true,
      "barred_until": null,
      "created_at": "2026-03-12T20:00:00Z"
    }
  ],
  "total": 1
}

NOTE: "barred_until" is null for permanent bans. Expired bans are auto-archived
and will not appear in this list.

⚠ If "trespassed" is true, display a prominent warning — this person has a
  formal trespass order and must not be admitted under any circumstances.

── Add a barred person from mobile ──────────────────────────────────────────────

POST /api/mobile/barred

Requires admin role OR the 'add_barred' permission.

REQUEST BODY:
{
  "name": "John Doe",               ← required
  "aliases": ["Johnny D"],          ← optional
  "photo": "data:image/jpeg;...",   ← optional, base64 image (max 50MB)
  "description": "Details...",      ← optional
  "trespassed": true,               ← optional, default false
  "barred_until": "2026-08-01T00:00:00Z"  ← optional, null = permanent
}

RESPONSE (200 OK):
  { "barred": { ...full barred person row } }

────────────────────────────────────────────────────────────────────────────────
9. SHIFT SWAPS — Request and manage shift swaps
────────────────────────────────────────────────────────────────────────────────

Status machine:
  pending_employee → (target accepts) → pending_manager → (manager approves) → approved
                   → (target declines) → declined
                                       → (manager declines) → declined

── List my swap requests ────────────────────────────────────────────────────────

GET /api/mobile/schedule/swap

QUERY PARAMETERS (all optional):
  ?status=pending_employee|pending_manager|approved|declined

RESPONSE (200 OK):
{
  "swaps": [
    {
      "id": 10,
      "status": "pending_manager",
      "message": "Can we swap? I have a family thing.",
      "decline_reason": null,
      "requester_id": 42,
      "target_id": 55,
      "employee_responded_at": "2026-05-04T20:00:00Z",
      "manager_responded_at": null,
      "created_at": "2026-05-04T18:00:00Z",
      "requester_name": "Alex Smith",
      "requester_avatar": null,
      "target_name": "Jamie Lee",
      "target_avatar": null,
      "requester_date": "2026-05-10",
      "requester_shift": "Evening",
      "requester_start": "17:00",
      "requester_end": "23:00",
      "target_date": "2026-05-11",
      "target_shift": "Morning",
      "target_start": "09:00",
      "target_end": "15:00",
      "status_detail": "Jamie Lee accepted! Waiting for a manager to approve."
    }
  ]
}

status_detail examples (vary by who is viewing):
  "Jane wants to swap shifts with you. Waiting for your response."
  "Waiting for Jane to accept or decline your swap request."
  "Jane accepted! Waiting for a manager to approve."
  "You accepted. Waiting for a manager to approve the swap."
  "Swap approved! Alice and Bob have swapped shifts."
  "Swap declined: Manager was unable to accommodate."

── Create a swap request ────────────────────────────────────────────────────────

POST /api/mobile/schedule/swap

REQUEST BODY:
{
  "my_schedule_id": 301,       ← your user_schedules.id
  "their_schedule_id": 402,    ← the other employee's user_schedules.id
  "target_user_id": 55,        ← the other employee's user id
  "message": "Can we swap?"    ← optional note
}

RESPONSE (200 OK):
  { "ok": true, "swap_id": 10 }

Side effect: push notification sent to the target employee.

ERROR RESPONSES:
  404 { "error": "Your schedule entry not found" }
  404 { "error": "Target schedule entry not found" }
  409 { "error": "A pending swap request already exists for that shift" }

── Respond to a swap request (target employee only) ─────────────────────────────

PATCH /api/mobile/schedule/swap

REQUEST BODY:
{
  "swap_id": 10,
  "action": "accept",           ← or "decline"
  "decline_reason": "..."       ← optional, only used when action = "decline"
}

RESPONSE (200 OK):
  { "ok": true }

Side effects:
  - accept: notifies requester ("accepted, waiting for manager") + all admins
  - decline: notifies requester with decline message

  "decline_reason": "..."       ← optional, only used when action = "decline"
}

  { "ok": true }

Side effect: push notification sent to the requesting employee.

ERROR RESPONSES:
  403 { "error": "Admin access required" }
  404 { "error": "Request not found" }
  409 { "error": "Request has already been reviewed" }


────────────────────────────────────────────────────────────────────────────────
11. PUSH NOTIFICATION TYPES
────────────────────────────────────────────────────────────────────────────────

Each push notification (and in-app notification) includes a "type" field:

  swap_request            — new swap request targeting you
  swap_accepted_employee  — your swap request was accepted by the other employee
  swap_declined           — your swap request was declined by the other employee
  swap_pending_approval   — (admin) both employees agreed, needs manager action
  swap_approved           — swap fully approved by manager
  swap_manager_declined   — swap declined by manager
  time_off_request        — (admin) employee submitted a time-off request
  time_off_approved       — your time-off request was approved
  time_off_declined       — your time-off request was declined

Use the "type" to deep-link into the appropriate screen when the user taps
a push notification.

── Server setup for push notifications ──────────────────────────────────────────

Set these environment variables on the server:

  FIREBASE_PROJECT_ID=your-firebase-project-id
  FIREBASE_SERVICE_ACCOUNT_JSON=<contents of serviceAccountKey.json, single line>

Push is silently disabled when these vars are not set.

On the mobile client:
  1. Get an FCM/APNs device token from the platform SDK after login.
  2. POST /api/mobile/device-token with { token, platform: 'ios'|'android' }.
  3. On logout, DELETE /api/mobile/device-token to unregister.


────────────────────────────────────────────────────────────────────────────────
12. ERROR HANDLING — Standard error responses
────────────────────────────────────────────────────────────────────────────────

All endpoints use standard HTTP status codes.

Status  Meaning
──────  ────────────────────────────────────────────────────────────────────────
200     Success
400     Bad request — missing or invalid input
401     Unauthorized — missing, expired, or invalid Bearer token
403     Forbidden — authenticated but insufficient permissions
404     Not found — resource or org does not exist
409     Conflict — wrong state, duplicate, etc.
410     Gone — invite token already used or expired
500     Internal server error

Error response body always follows this format:
  { "error": "Human-readable description of what went wrong" }

TOKEN EXPIRY HANDLING:
  When you receive a 401, the token has expired (7-day lifetime).
  Re-authenticate by calling POST /api/mobile/auth again and save the new token.

────────────────────────────────────────────────────────────────────────────────
14. SECURITY NOTES
────────────────────────────────────────────────────────────────────────────────

- Tokens are signed JWT (HS256). Never decode and trust the payload client-side
  for security decisions — the server validates the signature on every request.

- Store tokens ONLY in secure storage (Keychain / EncryptedSharedPreferences).
  Never store in AsyncStorage — it is unencrypted.

- Tokens expire after 7 days. Handle 401 responses by clearing the stored token
  and redirecting the user to the login screen.

- Invite tokens are single-use. Once a registration completes, the token is
  marked used and cannot be reused.

- All returned data is scoped to the authenticated user's organization. The
  server enforces this — it is not possible to access another org's data with
  a valid token from a different org.

- HTTPS is required. All endpoints are served over TLS only.
