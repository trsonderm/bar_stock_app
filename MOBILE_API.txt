================================================================================
  TOPSHELF INVENTORY — MOBILE API REFERENCE
  Base URL: https://www.topshelfInventory.com
  All data is scoped to the authenticated user's organization.
================================================================================


────────────────────────────────────────────────────────────────────────────────
OVERVIEW
────────────────────────────────────────────────────────────────────────────────

All mobile API endpoints live under /api/mobile/.

Authentication uses JWT Bearer tokens — not cookies.
  1. Call POST /api/mobile/auth to get a token.
  2. Include the token in every subsequent request:
       Authorization: Bearer <your-token>

Tokens expire after 7 days. Store them securely:
  iOS    → Keychain (via react-native-keychain or expo-secure-store)
  Android → EncryptedSharedPreferences or Keystore

Every response is JSON. Every request body must be JSON with the header:
  Content-Type: application/json

All data returned is filtered to the authenticated user's organization —
no cross-organization data leakage is possible.


────────────────────────────────────────────────────────────────────────────────
1. AUTHENTICATION — Login and get a token
────────────────────────────────────────────────────────────────────────────────

POST /api/mobile/auth

No Authorization header needed for this request.

REQUEST BODY:
{
  "organization_subdomain": "your-bar",     ← required (your org's subdomain)
  "email": "admin@yourbar.com",             ← use EITHER email+password
  "password": "yourpassword"
}

OR:
{
  "organization_subdomain": "your-bar",
  "pin": "1234"                             ← OR a 4-digit PIN
}

RESPONSE (200 OK):
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expires_in": 604800,
  "user": {
    "id": 42,
    "first_name": "Alex",
    "last_name": "Smith",
    "email": "admin@yourbar.com",
    "role": "admin",
    "permissions": ["all"]
  },
  "organization": {
    "id": 7,
    "name": "The Rusty Nail",
    "subdomain": "your-bar",
    "subscription_plan": "pro"
  }
}

ERROR RESPONSES:
  401 { "error": "Invalid credentials" }
  401 { "error": "Invalid PIN" }
  404 { "error": "Organization not found" }
  400 { "error": "Provide email+password or pin" }

USAGE AFTER LOGIN:
  Save the "token" value and send it on every future request:
    Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

── Who am I? — Get identity and permissions ─────────────────────────────────

GET /api/mobile/auth/me

Returns the authenticated user's full identity, permission strings, and
pre-computed capability flags. Call once after login to determine which features
to show. Cache the result for the session; call again after a permission change.

RESPONSE (200 OK):
{
  "user": {
    "id": 42,
    "role": "admin",
    "permissions": ["all"],
    "first_name": "Alex",
    "last_name": "Smith",
    "display_name": "Alex S.",
    "profile_picture": null,
    "position": "Head Bartender",
    "phone": "5550001234",
    "email": "alex@yourbar.com"
  },
  "organization": {
    "name": "The Rusty Nail",
    "subdomain": "your-bar",
    "subscription_plan": "pro"
  },
  "capabilities": {
    "can_add_stock": true,
    "can_subtract_stock": true,
    "can_add_barred": true,
    "can_delete_barred": true,
    "can_view_barred": true,
    "can_add_incident": true,
    "can_review_incidents": true,
    "can_receive_orders": true,
    "can_approve_swaps": true,
    "can_approve_time_off": true,
    "can_approve_schedule": true,
    "can_manage_inventory": true,
    "can_view_reports": true,
    "is_admin": true
  }
}

CAPABILITY LOGIC:
  can_add_stock         → is_admin OR permissions includes add_stock OR all
  can_subtract_stock    → is_admin OR permissions includes subtract_stock OR all
  can_view_barred       → is_admin OR add_barred OR delete_barred OR all
  can_add_incident      → is_admin OR permissions includes add_incident OR all
  can_review_incidents  → is_admin OR permissions includes review_incidents OR all
  can_receive_orders    → is_admin OR add_stock OR all
  can_approve_swaps     → is_admin only
  can_approve_time_off  → is_admin only
  is_admin              → role = "admin"

NOTE: Use this endpoint (not token decoding) to drive show/hide logic.
      JWT payloads are signed but decoding them client-side for auth decisions
      is a security anti-pattern. The server re-validates on every request.


────────────────────────────────────────────────────────────────────────────────
2. REGISTRATION — Join via admin invite link
────────────────────────────────────────────────────────────────────────────────

Admins generate invite links from Settings → Users → "Invite New User by Email."
The link looks like:
  https://www.topshelfInventory.com/register/invite?token=abc123...

The token in that URL is what the mobile app uses. No Authorization header
is needed for either registration endpoint.

── Step 1: Validate the token ──────────────────────────────────────────────────

GET /api/mobile/register?token=<invite-token>

RESPONSE (200 OK):
{
  "valid": true,
  "org_name": "The Rusty Nail",
  "email": "newstaff@yourbar.com",   ← pre-filled email (may be null)
  "role": "user"
}

ERROR RESPONSES:
  404 { "error": "Invalid token" }
  410 { "error": "Invitation already used" }
  410 { "error": "Invitation expired" }

── Step 2: Complete registration ────────────────────────────────────────────────

POST /api/mobile/register

REQUEST BODY:
{
  "token": "abc123...",              ← required — from the invite link
  "firstName": "Alex",              ← required
  "lastName": "Smith",              ← required
  "displayName": "Alex S.",         ← optional (shown in feed & messages)
  "email": "alex@yourbar.com",      ← required if not pre-filled by admin
  "phone": "5550001234",            ← optional
  "password": "mysecurepassword",   ← required, min 6 characters
  "pin": "1234"                     ← required, exactly 4 digits
}

RESPONSE (200 OK):
{
  "token": "eyJhbGciOiJIUzI1NiIs...",   ← save this, use as Bearer token
  "expires_in": 604800,
  "user": {
    "id": 55,
    "first_name": "Alex",
    "last_name": "Smith",
    "role": "user",
    "email": "alex@yourbar.com"
  },
  "organization": {
    "id": 7,
    "name": "The Rusty Nail"
  }
}

ERROR RESPONSES:
  400 { "error": "First and last name are required" }
  400 { "error": "Password must be at least 6 characters" }
  400 { "error": "PIN must be exactly 4 digits" }
  409 { "error": "Email already in use" }
  410 { "error": "Invitation already used" }
  410 { "error": "Invitation expired" }

NOTE: Each invite token can only be used once. After successful registration,
use the returned "token" exactly like any other Bearer token for all subsequent
API calls. The user is automatically assigned to all locations in the org.

────────────────────────────────────────────────────────────────────────────────

── Get low/out-of-stock items ──────────────────────────────────────────────────

GET /api/mobile/out-of-stock

QUERY PARAMETERS (all optional):
  ?location_id=2    Filter to a specific location ID

RESPONSE (200 OK):
{
  "items": [
    {
      "id": 88,
      "name": "Tito's Vodka 750ml",
      "type": "Liquor",
      "secondary_type": "Vodka",
      "quantity": 0,
      "low_stock_threshold": 3,
      "order_size": [{ "label": "Case", "amount": 12 }],
      "supplier": "Southern Glazers"
    }
  ],
  "total": 12,
  "out_of_stock": 4,
  "low_stock": 8
}

NOTES:
- "out_of_stock" = items with quantity exactly 0
- "low_stock" = items with quantity > 0 but <= low_stock_threshold
- Items sorted by quantity ascending (most urgent first)
- Only items with include_in_low_stock_alerts = true are returned

── Adjust stock quantity ───────────────────────────────────────────────────────

POST /api/mobile/stock/adjust

Required permissions: add_stock (for positive change) or subtract_stock (for negative change).
Admins (role = "admin" or permissions includes "all") can always adjust.

REQUEST BODY:
{
  "item_id": 88,           ← required
  "change": -1,            ← required, non-zero; negative = subtract, positive = add
  "location_id": 2,        ← optional — defaults to the user's first assigned location
  "note": "spilled bottle" ← optional, recorded in activity log
}

RESPONSE (200 OK):
{
  "item_id": 88,
  "item_name": "Tito's Vodka 750ml",
  "location_id": 2,
  "change": -1,
  "quantity_after": 4
}

ERROR RESPONSES:
  400 { "error": "item_id is required" }
  400 { "error": "change must be a non-zero number" }
  400 { "error": "No locations configured" }
  403 { "error": "Permission denied: add_stock required" }
  403 { "error": "Permission denied: subtract_stock required" }
  404 { "error": "Item not found" }
  404 { "error": "Location not found" }

NOTES:
- Quantity is floored at 0 (will never go negative).
- Each adjustment is written to the activity log (action: ADD_STOCK or SUBTRACT_STOCK).
- Do NOT call /api/v1/inventory/adjust from mobile — that endpoint requires an
  API key (tsk_live_...) and will reject JWT Bearer tokens with 401.


────────────────────────────────────────────────────────────────────────────────
8. SCHEDULE — View the org schedule
────────────────────────────────────────────────────────────────────────────────

GET /api/mobile/schedule

All results are automatically scoped to the authenticated user's organization.
You cannot retrieve another organization's schedule.

QUERY PARAMETERS (all optional):
  ?view=week|month         View mode hint (default: week — affects default range)
  ?start=YYYY-MM-DD        Range start date (inclusive)
  ?end=YYYY-MM-DD          Range end date (inclusive, defaults to start if omitted)
  ?location_id=<id>        Filter to a specific location ID

SCOPE: Every response only returns users who belong to the authenticated user's
organization. The "is_mine" flag marks shifts belonging to the current user.

── REQUEST VARIATIONS ───────────────────────────────────────────────────────────

Single day (today's schedule):
  GET /api/mobile/schedule?start=2026-05-04&end=2026-05-04

Single day (any specific date):
  GET /api/mobile/schedule?start=2026-05-10&end=2026-05-10

Single day filtered by location:
  GET /api/mobile/schedule?start=2026-05-04&end=2026-05-04&location_id=2

Current week (Mon–Sun, auto-computed by server):
  GET /api/mobile/schedule
  GET /api/mobile/schedule?view=week

Explicit week range:
  GET /api/mobile/schedule?start=2026-05-04&end=2026-05-10
  GET /api/mobile/schedule?view=week&start=2026-05-04&end=2026-05-10

Week filtered by location:
  GET /api/mobile/schedule?start=2026-05-04&end=2026-05-10&location_id=2

Current month (auto-computed by server):
  GET /api/mobile/schedule?view=month

Explicit month range:
  GET /api/mobile/schedule?start=2026-05-01&end=2026-05-31
  GET /api/mobile/schedule?view=month&start=2026-05-01&end=2026-05-31

Month filtered by location:
  GET /api/mobile/schedule?view=month&start=2026-05-01&end=2026-05-31&location_id=2

Multi-week or arbitrary range (any start/end you need):
  GET /api/mobile/schedule?start=2026-05-01&end=2026-05-21

Note: The server internally fetches one additional day before "start" to capture
overnight shifts that spill into the range start date. Those entries have
"is_pre_range": true so the client can filter them from display if needed.

── RESPONSE (200 OK) ────────────────────────────────────────────────────────────

{
  "schedules": [
    {
      "id": 301,
      "date": "2026-05-05",           ← always YYYY-MM-DD (local date, no timezone shift)
      "user_id": 42,
      "shift_id": 5,
      "recurring_group_id": null,
      "shift_name": "Evening",
      "start_time": "17:00",          ← HH:MM 24-hour format
      "end_time": "23:00",
      "color": "#1d4ed8",
      "user_name": "Alex Smith",
      "user_avatar": null,            ← base64 data-URL or null
      "position": "Head Bartender",
      "is_mine": true,                ← true only for the authenticated user's shifts
      "crosses_midnight": false,      ← true when start_time > end_time (overnight shift)
      "spillover_date": null,         ← YYYY-MM-DD of next day if crosses_midnight, else null
      "is_pre_range": false           ← true if this entry was from the day before requested start
    },
    {
      "id": 302,
      "date": "2026-05-05",
      "shift_name": "Closing",
      "start_time": "22:00",
      "end_time": "02:00",            ← end < start = overnight shift
      "crosses_midnight": true,
      "spillover_date": "2026-05-06", ← this shift continues into May 6
      "is_pre_range": false,
      ...
    }
  ],
  "pending_swaps": [ ...swap objects (see Shift Swaps section) ],
  "start": "2026-05-05",             ← the start date you requested
  "end": "2026-05-11",               ← the end date used
  "view": "week"
}

── OVERNIGHT SHIFTS ─────────────────────────────────────────────────────────────

When "crosses_midnight" is true, the shift starts on "date" and ends on
"spillover_date". The end_time is on the following calendar day.

To show overnight continuation in a day view:
  1. Display the shift normally on its "date" (show start_time, note "+1" on end_time)
  2. On "spillover_date", show a continuation entry using the same record:
       filter: schedules.filter(s => s.crosses_midnight && s.spillover_date === targetDate)
       display: "until <end_time>" with an "↩ overnight" badge

To check if a day has overnight continuation from the previous day:
  spillovers = schedules.filter(s => s.crosses_midnight && s.spillover_date === dateString)

── FILTERING ONLY YOUR OWN SHIFTS (client-side) ─────────────────────────────────

All schedules are returned for the org. To show only the authenticated user's shifts:
  myShifts = schedules.filter(s => s.is_mine === true)

── NOTES ────────────────────────────────────────────────────────────────────────

- All schedules are scoped to the authenticated user's organization automatically.
- "is_mine" flags shifts belonging to the authenticated user only.
- "pending_swaps" lists open swap requests involving the user — no extra call needed.
- Archived users are excluded from results.
- "color" comes from the shift definition. Use it for color-coding schedule blocks.
- Dates are always raw YYYY-MM-DD strings — compare as strings, not Date objects,
  to avoid timezone shift bugs (do not use new Date(s.date).getDate()).
- The "location_id" filter uses JOIN — users without a location assignment are
  excluded when this filter is active.


────────────────────────────────────────────────────────────────────────────────
9. SHIFT SWAPS — Request and manage shift swaps
────────────────────────────────────────────────────────────────────────────────

There are two types of swap requests:

  DIRECT — Requester selects a specific colleague and their shift to swap with.
  OPEN   — Requester posts their shift openly to all org members. Anyone can
           claim it. Supports both "swap" (two-way) and "give away" (one-way).

Status machines:

  Direct swap:
    pending_employee → (target accepts) → pending_manager → (manager approves) → approved
                     → (target declines) → declined
                                         → (manager declines) → declined

  Open request (swap or give away):
    open → (any employee claims via PUT) → pending_manager → (manager approves) → approved
                                                           → (manager declines) → declined

── List swap requests ───────────────────────────────────────────────────────────

GET /api/mobile/schedule/swap

Returns swap requests you're involved in (as requester or target), plus any
open org-wide requests currently in "open" status (claimable by you).

QUERY PARAMETERS (all optional):
  ?status=open|pending_employee|pending_manager|approved|declined

RESPONSE (200 OK):
{
  "swaps": [
    {
      "id": 10,
      "status": "pending_manager",
      "request_type": "direct",      ← "direct" | "open"
      "is_giveaway": false,           ← true = one-way giveaway, false = mutual swap
      "message": "Can we swap? I have a family thing.",
      "decline_reason": null,
      "requester_id": 42,
      "target_id": 55,               ← null for unclaimed open requests
      "employee_responded_at": "2026-05-04T20:00:00Z",
      "manager_responded_at": null,
      "created_at": "2026-05-04T18:00:00Z",
      "requester_name": "Alex Smith",
      "requester_avatar": null,
      "target_name": "Jamie Lee",    ← null for unclaimed open requests
      "target_avatar": null,
      "requester_date": "2026-05-10",
      "requester_shift": "Evening",
      "requester_start": "17:00",
      "requester_end": "23:00",
      "target_date": "2026-05-11",   ← null for giveaway or unclaimed open requests
      "target_shift": "Morning",
      "target_start": "09:00",
      "target_end": "15:00",
      "status_detail": "Jamie Lee accepted! Waiting for a manager to approve."
    }
  ]
}

status_detail strings (computed server-side, vary by who is viewing):

  Direct swap:
    "Jane wants to swap shifts with you. Waiting for your response."
    "Waiting for Jane to accept or decline your swap request."
    "Jane accepted! Waiting for a manager to approve."
    "You accepted. Waiting for a manager to approve the swap."
    "Swap approved! Alice and Bob have swapped shifts."
    "Swap declined: Manager was unable to accommodate."

  Open request (requester view):
    "You've posted your Evening shift on 2026-05-10 for anyone to take."
    "You've posted your Evening shift on 2026-05-10 as open for anyone to swap with."
    "Jamie Lee claimed your open shift request. Waiting for a manager to approve."

  Open request (other employees view):
    "Alex Smith is giving away their Evening shift on 2026-05-10. Tap to claim it."
    "Alex Smith is looking for someone to swap their Evening shift on 2026-05-10."

── Create a swap request ────────────────────────────────────────────────────────

POST /api/mobile/schedule/swap

DIRECT SWAP — target a specific colleague:
{
  "my_schedule_id": 301,       ← your user_schedules.id  (required)
  "their_schedule_id": 402,    ← colleague's user_schedules.id  (required for direct)
  "target_user_id": 55,        ← colleague's user id  (required for direct)
  "message": "Can we swap?"    ← optional note
}

OPEN REQUEST — broadcast to all org members:
{
  "my_schedule_id": 301,       ← your user_schedules.id  (required)
  "is_giveaway": true,         ← true = give away shift, false/omit = open swap
  "message": "Anyone free?"    ← optional note
}
Omit their_schedule_id and target_user_id entirely to create an open request.

RESPONSE (200 OK):
  { "ok": true, "swap_id": 10 }

Side effects:
  Direct: push notification sent to target employee.
  Open:   push notification broadcast to all org members.

ERROR RESPONSES:
  400 { "error": "my_schedule_id is required" }
  404 { "error": "Your schedule entry not found" }
  404 { "error": "Target schedule entry not found" }
  409 { "error": "A pending swap request already exists for that shift" }

── Claim an open request ────────────────────────────────────────────────────────

PUT /api/mobile/schedule/swap

Any org member can claim an open request. For open swaps (is_giveaway=false),
provide your schedule entry. For give-aways, no schedule entry is needed —
you're simply agreeing to cover the shift.

REQUEST BODY:
{
  "swap_id": 10,               ← required
  "my_schedule_id": 205        ← required for open swaps, omit for give-aways
}

RESPONSE (200 OK):
  { "ok": true }

Side effects: notifies the requester that their shift was claimed + notifies
all admins that manager approval is needed. Status moves to pending_manager.

ERROR RESPONSES:
  400 { "error": "swap_id is required" }
  400 { "error": "This is not an open request" }
  400 { "error": "You cannot claim your own request" }
  400 { "error": "my_schedule_id is required to claim a swap request" }
  404 { "error": "Swap request not found" }
  404 { "error": "Your schedule entry not found" }
  409 { "error": "This request is no longer open" }

── Respond to a direct swap request (target employee only) ──────────────────────

PATCH /api/mobile/schedule/swap

Only the designated target employee of a direct swap uses this endpoint.
Open requests use PUT (claim) above instead.

REQUEST BODY:
{
  "swap_id": 10,
  "action": "accept",           ← or "decline"
  "decline_reason": "..."       ← optional, only used when action = "decline"
}

RESPONSE (200 OK):
  { "ok": true }

Side effects:
  - accept: status → pending_manager; notifies requester + all admins
  - decline: status → declined; notifies requester with decline message

────────────────────────────────────────────────────────────────────────────────
11. MESSAGING — Direct and group messages between employees
────────────────────────────────────────────────────────────────────────────────

Messaging uses a thread model. A thread is either "direct" (1-on-1) or "group"
(2+ other recipients). You always appear in the thread as a member.

── DB MIGRATION REQUIRED ────────────────────────────────────────────────────────

Before using messaging, run the migration on the server:
  psql -U postgres topshelf -f scripts/mobile-features-migration.sql

This creates: message_threads, message_thread_members, direct_messages,
              mobile_user_settings

── List threads (inbox) ─────────────────────────────────────────────────────────

GET /api/mobile/messages

RESPONSE (200 OK):
{
  "threads": [
    {
      "id": 1,
      "type": "direct",                          ← "direct" or "group"
      "name": null,                              ← group name (null for direct)
      "updated_at": "2026-05-05T12:00:00Z",
      "members": [
        {
          "id": 55,
          "name": "Jamie Lee",
          "avatar": "data:image/jpeg;base64,...",
          "position": "Bartender"
        }
      ],
      "last_message": {
        "id": 200,
        "content": "See you tonight!",
        "sender_id": 55,
        "created_at": "2026-05-05T11:58:00Z"
      },
      "unread_count": 2
    }
  ]
}

NOTES:
- "members" excludes yourself — it is the other people in the thread.
- "unread_count" counts messages sent by others after your last_read_at timestamp.
- Threads are sorted newest-updated first.
- For direct threads, derive the thread display name from members[0].name.

── Start a new thread or send an initial message ────────────────────────────────

POST /api/mobile/messages

REQUEST BODY:
{
  "user_ids": [55],                   ← required: who to message (not yourself)
  "message": "Hey, are you working tonight?",  ← at least one of message/image required
  "image": "data:image/jpeg;base64,...",       ← optional, base64 data-URI
  "thread_name": "Closing Crew"       ← optional, only used for group threads (user_ids.length > 1)
}

BEHAVIOR:
- user_ids.length === 1 → direct thread. If a direct thread already exists between
  you and that user, the message is added to it (no duplicate threads).
- user_ids.length >= 2  → group thread. Always creates a new thread.
- You do not need to include yourself in user_ids — the server adds you automatically.
- All user_ids must belong to your organization; mismatches return 400.

RESPONSE (200 OK):
{
  "ok": true,
  "thread_id": 1,
  "message_id": 200,
  "created_at": "2026-05-05T12:00:00Z"
}

Side effect: FCM push notification sent to all recipients.

ERROR RESPONSES:
  400 { "error": "user_ids required" }
  400 { "error": "message or image required" }
  400 { "error": "image must be a base64 data-URI" }
  400 { "error": "One or more users not found in your organization" }

── Get messages in a thread (paginated) ─────────────────────────────────────────

GET /api/mobile/messages/<threadId>

QUERY PARAMETERS (all optional):
  ?limit=50        Max messages to return (default: 50, max: 100)
  ?before=<ISO>    Cursor for pagination: return messages older than this timestamp

Automatically marks the thread as read for your user.

RESPONSE (200 OK):
{
  "thread": {
    "id": 1,
    "type": "direct",
    "name": null,
    "members": [ { "id": 55, "name": "Jamie Lee", "avatar": null, "position": "Bartender" } ]
  },
  "messages": [
    {
      "id": 198,
      "sender_id": 55,
      "content": "Hey!",
      "image": null,
      "created_at": "2026-05-05T11:55:00Z",
      "sender_name": "Jamie Lee",
      "sender_avatar": null
    },
    {
      "id": 199,
      "sender_id": 42,
      "content": "What's up?",
      "image": null,
      "created_at": "2026-05-05T11:57:00Z",
      "sender_name": "Alex Smith",
      "sender_avatar": null
    }
  ],
  "has_more": false    ← true if there are older messages; paginate with ?before=<oldest created_at>
}

NOTES:
- Messages are returned oldest-first (ascending created_at).
- For pagination: take the oldest message's created_at and pass it as ?before=<ISO>.
- "image" is a base64 data-URI string or null.
- To show images: if message.image is not null, render it as an <Image> instead of text.

── Send a message to an existing thread ─────────────────────────────────────────

POST /api/mobile/messages/<threadId>

REQUEST BODY:
{
  "message": "On my way!",                       ← at least one of message/image required
  "image":   "data:image/jpeg;base64,..."        ← optional
}

RESPONSE (200 OK):
{
  "ok": true,
  "message_id": 201,
  "created_at": "2026-05-05T12:10:00Z"
}

Side effect: FCM push sent to all thread members except you.

── Leave a thread ────────────────────────────────────────────────────────────────

DELETE /api/mobile/messages/<threadId>

Removes you from the thread's member list. The thread and its messages are preserved
for the remaining members. You will no longer receive push notifications for it.

RESPONSE (200 OK):
  { "ok": true }

── Live messaging — polling for new messages ─────────────────────────────────────

GET /api/mobile/messages/poll?since=<ISO>

Returns all new messages across ALL your threads since the given timestamp.
Also returns updated unread counts for affected threads.

Use this to keep the inbox live while the app is in the foreground.
Recommended interval: every 5–8 seconds while the messages screen is open.

For background updates: rely on FCM push (type: "new_message"). When a push
arrives, call GET /api/mobile/messages/poll?since=<last_poll_time> to refresh.

REQUEST:
  GET /api/mobile/messages/poll?since=2026-05-05T12:00:00.000Z

RESPONSE (200 OK):
{
  "messages": [
    {
      "id": 202,
      "thread_id": 1,
      "sender_id": 55,
      "content": "Are you there?",
      "image": null,
      "created_at": "2026-05-05T12:02:00Z",
      "sender_name": "Jamie Lee",
      "sender_avatar": null
    }
  ],
  "unread": [
    { "thread_id": 1, "unread_count": "1" }
  ],
  "server_time": "2026-05-05T12:02:05.123Z"   ← use this as your next "since" value
}

POLLING IMPLEMENTATION PATTERN:
  let lastPollTime = new Date().toISOString();
  setInterval(async () => {
    const res = await fetch(`/api/mobile/messages/poll?since=${lastPollTime}`, { headers });
    const { messages, unread, server_time } = await res.json();
    lastPollTime = server_time;   // always advance to server_time, not client Date.now()
    if (messages.length > 0) updateUI(messages, unread);
  }, 6000);

ERROR RESPONSES:
  400 { "error": "since param required (ISO timestamp)" }
  400 { "error": "since must be a valid ISO timestamp" }

15. ORDERS — View and check in incoming stock deliveries
────────────────────────────────────────────────────────────────────────────────

Orders are purchase orders created by admins or the AI ordering system.
Mobile staff use these endpoints to see what deliveries are expected and to
check in items when a delivery arrives (updating inventory automatically).

Check-in requires the add_stock permission or admin role.

── List orders ──────────────────────────────────────────────────────────────────

GET /api/mobile/orders

Returns orders sorted by urgency (IN_TRANSIT first, then PARTIALLY_RECEIVED,
then PENDING), then by expected delivery date.

QUERY PARAMETERS (all optional):

                              ?status=PENDING,IN_TRANSIT
                            Use ?status=all for all statuses.

  ?location_id=2            Filter to a specific location
  ?limit=50                 Page size (default: 50, max: 100)
  ?offset=0                 Pagination offset

Valid statuses: PENDING | IN_TRANSIT | PARTIALLY_RECEIVED | DELIVERED | CANCELLED

RESPONSE (200 OK):
{
  "orders": [
    {
      "id": 10,
      "status": "IN_TRANSIT",
      "location_id": 2,
      "location_name": "Main Bar",
      "expected_delivery": "2026-05-20",
      "notes": "Call supplier if not arrived by noon",
      "item_count": 5,
      "total_units": 60,
      "units_received": 0,
      "created_at": "2026-05-15T09:00:00Z",
      "updated_at": "2026-05-15T09:00:00Z"
    }
  ],
  "total": 3,
  "limit": 50,
  "offset": 0
}

── Get order details ────────────────────────────────────────────────────────────

GET /api/mobile/orders/<id>

RESPONSE (200 OK):
{
  "order": {
    "id": 10,
    "status": "IN_TRANSIT",
    "location_id": 2,
    "location_name": "Main Bar",
    "expected_delivery": "2026-05-20",
    "notes": null,
    "created_at": "2026-05-15T09:00:00Z",
    "updated_at": "2026-05-15T09:00:00Z",
    "items": [
      {
        "id": 55,              ← order_item_id (use this in the check-in POST)
        "item_id": 88,
        "item_name": "Tito's Vodka 750ml",
        "type": "Liquor",
        "supplier": "Southern Glazers",
        "quantity_ordered": 12,
        "quantity_received": null,  ← null = not yet received
        "unit_cost": 14.50
      }
    ]
  }
}

── Check in / receive an order ──────────────────────────────────────────────────

POST /api/mobile/orders/<id>

Requires add_stock permission or admin.

For each item in the body, sets quantity_received and adds that amount to
inventory at the order's location. The order status updates automatically:
  All items fully received  → DELIVERED
  Some items received       → PARTIALLY_RECEIVED

Call multiple times (partial deliveries) — quantities accumulate.

REQUEST BODY:
{
  "items": [
    { "order_item_id": 55, "quantity_received": 12 },
    { "order_item_id": 56, "quantity_received": 6 }
  ]
}

quantity_received is capped at the ordered quantity per item.

RESPONSE (200 OK):
{
  "ok": true,
  "order_id": 10,
  "status": "DELIVERED",
  "items_received": [
    { "order_item_id": 55, "item_id": 88, "quantity_received": 12 },
    { "order_item_id": 56, "item_id": 91, "quantity_received": 6 }
  ]
}

ERROR RESPONSES:
  400 { "error": "items must be a non-empty array" }
  403 { "error": "Permission denied: add_stock required" }
  404 { "error": "Order not found" }
  409 { "error": "Cannot receive items on a DELIVERED order" }
  409 { "error": "Cannot receive items on a CANCELLED order" }

NOTES:
- Each received quantity is written to the activity_log as ADD_STOCK.
- Inventory is updated at the order's location_id (not the user's location).
- Items omitted from the POST body are not modified.


────────────────────────────────────────────────────────────────────────────────
17. PUSH NOTIFICATION TYPES
────────────────────────────────────────────────────────────────────────────────

Each push notification (and in-app notification) includes a "type" field:

  new_message             — new direct or group message (data: thread_id, sender_id)
  post_liked              — someone liked your post (data: post_id)
  post_comment            — new comment on a post you engaged with (data: post_id)
  swap_request            — new swap request targeting you
  swap_accepted_employee  — your swap request was accepted by the other employee
  swap_declined           — your swap request was declined by the other employee
  swap_pending_approval   — (admin) both employees agreed, needs manager action
  swap_approved           — swap fully approved by manager
  swap_manager_declined   — swap declined by manager
  time_off_request        — (admin) employee submitted a time-off request
  time_off_approved       — your time-off request was approved
  time_off_declined       — your time-off request was declined

Use the "type" to deep-link into the appropriate screen when the user taps
a push notification:
  new_message   → navigate to Messages screen, open thread with thread_id
  post_liked    → navigate to Feed, highlight post with post_id
  post_comment  → navigate to Feed, open comments for post_id
  swap_*        → navigate to Schedule → Swaps tab
  time_off_*    → navigate to Schedule → Time Off tab

── Server setup for push notifications ──────────────────────────────────────────

Set these environment variables on the server:

  FIREBASE_PROJECT_ID=your-firebase-project-id
  FIREBASE_SERVICE_ACCOUNT_JSON=<contents of serviceAccountKey.json, single line>

Push is silently disabled when these vars are not set.

On the mobile client:
  1. Get an FCM/APNs device token from the platform SDK after login.
  2. POST /api/mobile/device-token with { token, platform: 'ios'|'android' }.
  3. On logout, DELETE /api/mobile/device-token to unregister.

15. RECIPES — Browse drink recipes
────────────────────────────────────────────────────────────────────────────────

⚠ IMPORTANT — USE THE CORRECT ENDPOINT:

  Mobile apps must call  GET /api/mobile/recipes
                   NOT   GET /api/v1/recipes

  /api/v1/recipes is the Developer API — it requires a static API key
  (tsk_live_…), not a Bearer JWT, and returns a DIFFERENT response shape:
    { "data": [...], "meta": { "api_version", "total", "limit", "offset" } }

  Calling /api/v1/recipes from a mobile JWT session will return HTTP 200 but
  the response envelope will not contain a "recipes" key, causing "Could not
  parse JSON from server" errors in the app. Always use /api/mobile/recipes.

The org's recipe library blends two sources:
  • Local  — recipes created by your org's admins (org_recipes table)
  • Global — curated recipes managed by TopShelf staff (read-only)

Which sources are searched is controlled by the org's General Settings
(recipe_search_source: "local" | "global" | "both").  The ?source param
overrides this per request.

RECIPE ID FORMAT
  l:<id>   org-local recipe (e.g. "l:3")
  g:<id>   global recipe    (e.g. "g:12")

── List / search recipes ────────────────────────────────────────────────────────

GET /api/mobile/recipes

QUERY PARAMETERS (all optional):
  ?q=margarita     Full-text search across name and description

  ?source=local    "local" | "global" | "both" — overrides org setting
  ?limit=50        Page size (default 50, max 200)
  ?offset=0        Page offset (default 0)

────────────────────────────────────────────────────────────────────────────────
16. ERROR HANDLING — Standard error responses
────────────────────────────────────────────────────────────────────────────────

All endpoints use standard HTTP status codes.

Status  Meaning
──────  ────────────────────────────────────────────────────────────────────────
200     Success
400     Bad request — missing or invalid input
401     Unauthorized — missing, expired, or invalid Bearer token
403     Forbidden — authenticated but insufficient permissions
404     Not found — resource or org does not exist
409     Conflict — wrong state, duplicate, etc.
410     Gone — invite token already used or expired
500     Internal server error

Error response body always follows this format:
  { "error": "Human-readable description of what went wrong" }

TOKEN EXPIRY HANDLING:
  When you receive a 401, the token has expired (7-day lifetime).
  Re-authenticate by calling POST /api/mobile/auth again and save the new token.

The mobile incident form should be presented as a scrollable single-screen form

SECTION 1 — DATE & TIME

  incident_time    Time picker         Auto-populate with current time; user can change

  media            Multi-file picker   Photos and videos for the whole incident

    first_name            Text input       Optional

POST /api/mobile/admin/schedule/entries
  Create one or more schedule entries (assign users to a shift).
  Body:
  {
    "userIds":     [3, 5, 7],           ← required; one or more user IDs
    "shiftId":     2,                   ← required; shift template ID
    "dates":       ["2026-07-14", "2026-07-15", "2026-07-16"],  ← required; ISO dates
    "locationId":  null,                ← optional; scope the entry to a location

  Update a schedule entry. Use modifyStrategy to handle recurring sets.
  Body:

    "instance"  — edit only this one entry (detaches from recurring group)
    "following" — edit this entry and all future entries in the same recurring group
    "all"       — edit every entry in the recurring group (past and future)

  RESPONSE: { "ok": true }

DELETE /api/mobile/admin/schedule/entries
  Body: { "id": 101, "modifyStrategy": "instance" }

  RESPONSE: { "ok": true }

19. SECURITY NOTES
────────────────────────────────────────────────────────────────────────────────

- Tokens are signed JWT (HS256). Never decode and trust the payload client-side
  for security decisions — the server validates the signature on every request.

- Store tokens ONLY in secure storage (Keychain / EncryptedSharedPreferences).
  Never store in AsyncStorage — it is unencrypted.

- Tokens expire after 7 days. Handle 401 responses by clearing the stored token
  and redirecting the user to the login screen.

- Invite tokens are single-use. Once a registration completes, the token is
  marked used and cannot be reused.

- All returned data is scoped to the authenticated user's organization. The
  server enforces this — it is not possible to access another org's data with
  a valid token from a different org.

- HTTPS is required. All endpoints are served over TLS only.

- Passwords and PINs are NEVER returned by any API endpoint. They are stored
  as bcrypt hashes (password_hash, pin_hash). If you observe a raw password
  in any response, treat it as a security incident.

- Image uploads (profile picture, message images) are validated server-side:
  must start with "data:image/", must be within size limits. Never trust the
  content-type from the client alone.

- Thread membership is enforced on every message read/send. You cannot read
  or send to a thread you are not a member of, even if you know the thread ID.

- All user lookups for messaging validate that target users belong to the same
  organization before creating threads. Cross-org messaging is impossible.

- The poll endpoint (/messages/poll) uses the server's current timestamp in
  its response ("server_time"). Always advance your "since" cursor to this
  value, not to client clock, to avoid clock-skew gaps or double-delivers.

────────────────────────────────────────────────────────────────────────────────
OVERVIEW
────────────────────────────────────────────────────────────────────────────────

The Developer API is a separate, versioned API from the Mobile API. It uses
static API keys instead of JWT tokens and is intended for server-to-server
integrations, POS systems, custom dashboards, and automation scripts.

Key differences from the Mobile API:
  - Auth:        Bearer API key (tsk_live_…) instead of JWT token
  - Base path:   /api/v1/  instead of /api/mobile/
  - Scopes:      Keys are created with specific scopes limiting what they can do
  - Response:    Standard envelope { data, meta } on every response
  - Audience:    Server-side integrations, not end-user mobile apps

API keys are created by admins at: Admin → Settings → Developer API
Keys are scoped to a single organization. Each key grants only the scopes
selected at creation time.

Authentication:
  All requests must include the Authorization header:
    Authorization: Bearer tsk_live_<your-key>

Every request body must use JSON with the header:
  Content-Type: application/json

All data is scoped to the organization that owns the API key.


────────────────────────────────────────────────────────────────────────────────
STANDARD RESPONSE ENVELOPE
────────────────────────────────────────────────────────────────────────────────

Every v1 response wraps data in a consistent envelope:

Success (single resource):
{
  "data": { ...resource fields },
  "meta": {
    "api_version": "v1",
    "request_id": "a3f8b2c1d4e5f6a7",
    "timestamp": "2026-05-09T14:00:00.000Z"
  }
}

Success (list):
{
  "data": [ ...array of resources ],
  "meta": {
    "api_version": "v1",
    "request_id": "a3f8b2c1d4e5f6a7",
    "timestamp": "2026-05-09T14:00:00.000Z",
    "total": 142,
    "limit": 100,
    "offset": 0
  }
}

Error:
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Item not found."
  },
  "meta": {
    "api_version": "v1",
    "request_id": "a3f8b2c1d4e5f6a7",
    "timestamp": "2026-05-09T14:00:00.000Z"
  }
}

Error codes:
  UNAUTHORIZED   — missing or invalid API key (HTTP 401)
  FORBIDDEN      — key lacks the required scope (HTTP 403)
  BAD_REQUEST    — missing or invalid parameters (HTTP 400)
  NOT_FOUND      — resource does not exist (HTTP 404)
  INTERNAL_ERROR — server-side error (HTTP 500)

Required scope: audits:read

Returns audit sessions grouped by auditor and timestamp (minute granularity).

QUERY PARAMETERS (all optional):
  ?limit=50     Page size (default 50, max 200)
  ?offset=0     Page offset

RESPONSE (200 OK):
{
  "data": [
    {
      "session_id": 8801,

      "session_id" is the minimum activity_log ID in that session — use it

── Submit an audit ───────────────────────────────────────────────────────────────

POST /api/v1/audits
Required scope: audits:write

Set the actual (counted) quantities for items at a location. This OVERWRITES
current quantities with the actual values counted. Variance (actual - previous)
is calculated automatically and logged.

REQUEST BODY:
{
  "location_id": 1,           ← required
  "label": "Weekly count",    ← optional, recorded in the activity log
  "items": [                  ← required, non-empty array
    { "item_id": 1, "actual_quantity": 22, "note": "2 broken" },
    { "item_id": 5, "actual_quantity": 8 }
  ]
}

"items" fields:
  item_id          integer  required
  actual_quantity  number   required — the true counted quantity (can be 0)
  note             string   optional — recorded alongside this item's audit entry

RESPONSE (201 Created):
{
  "data": {
    "location_id": 1,
    "label": "Weekly count",
    "items_audited": 2,
    "items": [
      {
        "item_id": 1,
        "item_name": "Vodka",
        "previous_quantity": 24,
        "actual_quantity": 22,
        "variance": -2
      },
      {
        "item_id": 5,
        "item_name": "Gin",
        "previous_quantity": 6,
        "actual_quantity": 8,
        "variance": 2
      }
    ]
  },
  "meta": { ... }
}

ERROR RESPONSES:
  404 — location_id not found
  400 — items array is empty

NOTE: Items not found in this organization are silently skipped.
      All changes are applied atomically in a single transaction.
      Activity logs are written with source: "api" and the key name.

25. DEVELOPER API — RECIPES
────────────────────────────────────────────────────────────────────────────────

TopShelf supports two recipe libraries:
  • Org-local  — recipes your admin creates, readable and writable via the API
  • Global     — curated recipes managed by TopShelf staff, read-only via the API

Which libraries are searched is configured per-org in General Settings
(recipe_search_source: "local" | "global" | "both"). The ?source query param
overrides this per request.

RECIPE ID FORMAT
  l:<id>   org-local recipe (e.g. "l:3")
  g:<id>   global recipe    (e.g. "g:12")
  <int>    plain integer — resolves local first, then global

Only local recipes (l: prefix or plain integer) can be created, updated,
deleted, or have images uploaded via the API. Global recipes are read-only.

────────────────────────────────────────────────────────────────────────────────
GET /api/v1/recipes
────────────────────────────────────────────────────────────────────────────────
Scope: recipes:read

List drink recipes according to the org's recipe_search_source setting.
Results are merged with the primary library first, deduplicating by name.

QUERY PARAMS:
  q          string   Full-text search across name and description
  category   string   Filter by category ("Cocktail", "Shot", "Mocktail", etc.)
  source     string   "local" | "global" | "both" — overrides org setting
  limit      integer  Page size (default 50, max 200)
  offset     integer  Page offset (default 0)

24. DEVELOPER API — SECURITY NOTES
────────────────────────────────────────────────────────────────────────────────

- API keys start with tsk_live_. Store them in environment variables or a
  secrets manager — never hardcode them in source code or commit them.

- Keys are shown in full only once at creation. After that, only the prefix
  (first 8 characters) is visible in the admin UI. If a key is lost, revoke
  it and create a new one.

- Revoke unused keys immediately. Each key has a name and last-used timestamp
  visible in the admin UI to help identify stale credentials.

- Assign the minimum scopes needed. A key for a POS system reading stock
  levels only needs inventory:read — not inventory:write or orders:write.

- All API activity is logged in activity_logs with source: "api" and the
  key name. Audit trails are preserved for compliance.

- Keys are scoped to one organization. A key from Org A cannot access Org B's
  data under any circumstances.

- HTTPS is required. All endpoints are served over TLS only.

25. DATA SYNC — LIGHTWEIGHT CHANGE DETECTION FOR MOBILE
================================================================================

Mobile apps can poll a single lightweight endpoint to learn which data types
have changed since the last sync, then selectively download only the stale
data. This avoids unnecessary full-refresh calls on every app launch.

Authentication: Bearer JWT (same mobile token used by all /api/mobile/* routes)

────────────────────────────────────────────────────────────────────────────────
GET /api/mobile/sync
────────────────────────────────────────────────────────────────────────────────
Returns the most-recent change timestamp for every data type this org has
changed. Optional `since` parameter causes the response to also include a
`stale` array of data types that were updated after that timestamp.

QUERY PARAMS:
  since        ISO 8601 timestamp   Optional. When provided, the response
                                    includes a `stale` array listing all
                                    data types updated after this timestamp.
                                    Omit to receive all timestamps without
                                    a stale list (e.g., on first launch).

  location_id  integer              Optional. Include location-specific rows
                                    alongside org-wide rows. Defaults to 0
                                    (org-wide only).

RESPONSE 200:
{
  "server_time": "2026-07-11T12:00:00.000Z",
  "organization_id": 1,
  "location_id": 0,
  "stale": ["schedule", "inventory"],   // present only when `since` supplied
  "data": {
    "products":      { "updated_at": "2026-07-10T09:00:00.000Z", "endpoint": "/api/mobile/products" },
    "categories":    { "updated_at": "2026-07-09T14:30:00.000Z", "endpoint": "/api/mobile/admin/categories" },
    "suppliers":     { "updated_at": "2026-07-09T14:30:00.000Z", "endpoint": "/api/mobile/admin/suppliers" },
    "inventory":     { "updated_at": "2026-07-11T11:55:00.000Z", "endpoint": "/api/mobile/inventory" },
    "stock":         { "updated_at": "2026-07-11T11:55:00.000Z", "endpoint": "/api/mobile/stock" },
    "schedule":      { "updated_at": "2026-07-11T12:00:00.000Z", "endpoint": "/api/mobile/schedule" },
    "messages":      { "updated_at": "2026-07-10T18:00:00.000Z", "endpoint": "/api/mobile/messages" },
    "users":         { "updated_at": "2026-07-09T10:00:00.000Z", "endpoint": "/api/mobile/admin/users" },
    "settings":      { "updated_at": "2026-07-08T08:00:00.000Z", "endpoint": "/api/mobile/settings" },
    "recipes":       { "updated_at": "2026-07-05T10:00:00.000Z", "endpoint": "/api/mobile/recipes" },
    "orders":        { "updated_at": "2026-07-11T09:00:00.000Z", "endpoint": "/api/mobile/orders" },
    "bar_map":       { "updated_at": "2026-07-07T15:00:00.000Z", "endpoint": "/api/admin/bar-map" },
    "security":      { "updated_at": "2026-07-06T22:00:00.000Z", "endpoint": "/api/mobile/barred" },
    "locations":     { "updated_at": "2026-07-01T12:00:00.000Z", "endpoint": "/api/mobile/admin/locations" },
    "pricing_bands": { "updated_at": "2026-07-01T12:00:00.000Z", "endpoint": "/api/mobile/admin/pricing-bands" }
  }
}

NOTE: Only data types that have ever been changed appear in `data`. A data type
absent from `data` means no admin has ever mutated it — treat it as never
needing a refresh, or perform a full refresh on first launch.

RESPONSE 401: Missing or invalid Bearer token

────────────────────────────────────────────────────────────────────────────────
RECOMMENDED POLLING PATTERN
────────────────────────────────────────────────────────────────────────────────
1. On app launch, load the last-synced ISO timestamp from local storage.
2. Call GET /api/mobile/sync?since=<last_synced>.
3. For each data_type in the `stale` array, call the corresponding `endpoint`
   to download fresh data and update local storage.
4. Save `server_time` as the new last-synced timestamp.
5. On subsequent foreground resumes, repeat from step 2.

Example using location-specific data:
  GET /api/mobile/sync?since=2026-07-11T00:00:00.000Z&location_id=3

This returns schedule/inventory rows that are stale for either the whole org
or specifically for location 3.

────────────────────────────────────────────────────────────────────────────────
DATA TYPES TRACKED AND WHEN THEY ARE MARKED STALE
────────────────────────────────────────────────────────────────────────────────

  products       Items added, bulk-edited, imported, or archived
  categories     Category created, updated, or deleted
  suppliers      Supplier created or deleted
  inventory      Inventory quantity adjusted (admin or mobile)
  stock          Same events as inventory (synonym for stock-level view)
  schedule       Shift schedule created, updated, or deleted
  messages       Admin message sent
  users          Staff member created, updated, or deleted
  settings       Organization settings saved
  recipes        Recipe created
  orders         Purchase order created
  bar_map        Bar floor-plan map saved
  security       Barred person added, edited, restored, or removed;
                 security incident filed
  locations      Location created, updated, or deleted
  pricing_bands  Pricing band updated

BAR MAP API (admin session required — use admin web session cookie)

  Body: { transcript: string }
  Response: { "ok": true, "map_data": { ... }, "description": string }
